# 按能力扩展 Matter 桥接

本轮补齐此前只显示温度/湿度或完全禁用的部分控制。映射按 MIoT 服务语义、同一服务实例的属性名称、类型、权限和范围生成，不按家庭设备名称或型号串猜控制。既有卷帘驱动负责其型号的身份与协议限制；Matter 层只接收驱动提供的能力和缓存，不增加另一个 LAN 读取实现。

## 来自本地的依据与限制

2026-11-14 的脱敏报告只读取配置元数据、已有缓存规格和已有日志：12 台已接入设备、7 种型号，33 个服务、143 个属性。四条跳过导入记录不计为已接入；没有为缺失规格联网探测设备。六台卷帘的缓存房间全部为「阳台」，不从名称猜房间。

普通设备近期日志主要只有逐属性返回码；code=0 不能推断当前电源、温度、湿度或故障状态。11 月 6 日接收的历史只读转录（原始采样时间未取得）与当前读数分开：除湿机 22.1℃、毛巾架 59℃、壁炉加热关/照明开等仅用于构造明确标为模拟的回归，不能作为当前状态。当前不需要新增实机查询。

历史饮水机 fault 为布尔 true、喂食器 5.3/5.4/5.6 为数值 0，与缓存类型冲突，继续保留冲突，不进行真假转换。饮水机 2.11、9.16、9.17 在现存日志中为 -4001；本轮不通过降低校验或将这些属性桥接来规避错误。

## 实现后的映射

| 缓存能力/设备例子 | 本轮可发布 | 仍未发布 |
|---|---|---|
| 已有可信卷帘驱动；家中六台杜亚卷帘 | Window Covering：实际位置、目标、开、关、停 | 反向、校准、厂商模式；2.5 在正常路径始终禁用 |
| 主服务提供可读写布尔 on；例如除湿机 | 标准开关端点，另保留温度/湿度端点 | 目标湿度、智能/睡眠/干衣模式 |
| 加热服务提供主电源、可读摄氏温度、可写摄氏目标和范围；例如毛巾架 | Heating Thermostat：Heat/Off、本机温度、目标温度，保留独立温度传感端点 | 倒计时、厂商模式；本机表面温度不能当室温 |
| 壁炉的 heater/on 与独立 light/on | 加热电源与照明电源两个独立端点 | 加热档位、灯场景/RGB；无当前/目标温度，不能创建恒温器 |
| 饮水机、喂食器只有模式、状态、锁定或一次性动作 | 清楚显示当前无映射的原因 | 不把童锁/模式/喂食动作当主电源或可自动重试开关 |
| 已有灯、插座、风扇、净化器及传感器 | 保持原有映射 | 既有不支持项继续列明 |

通用电源使用 Matter 标准 On/Off Plug-in Unit，Aqara/Apple 平台可能将其显示为插座，设置页明确提示。它只绑定真实主电源，不能替代除湿目标、档位或喂食动作。当前 matter.js 0.18.0 没有本桥接已实现的标准除湿目标/宠物设备控制映射；本轮不创造厂商自定义集群来声称这些控制已可用。

恒温目标以百分之一摄氏度传递，使用设备声明的范围和步长，例如毛巾架 40–65℃、5℃步长；61℃会被拒绝，不静默改为 60℃。只开放 Heat/Off，拒绝 Cool/Auto。没有可靠的读数时保持不可达；缺失本机温度不补成室温。

设置页按设备列出已桥接能力与部分未桥接控制，名称、缓存房间靠左，选择开关靠右。设备选择与 HomeKit 独立，配对存储不重置。既有传感器端点 ID 保持原样；新增端点可能在平台里成为多个配件。升级前已有的同类型端点继续使用原 ID，不通过重新配对消除重复配件。

## 卷帘控制与状态来源

- 普通 App/自动轮询、Matter 控制共用既有 `CurtainControlController` / `CurtainControlSession`，身份校验、五属性校验、请求串行和停止优先级继续有效。
- 正常完整校验为 SIID 2 的 PIID `[2,3,4,9,10]`；普通状态为 `[2,3]`，写后确认使用实际位置与电机状态。不存在隐含六属性回退。
- Matter 目标百分比先转换为原生百分比；位置写入 `2.4=0…100`，全开 `2.1=2`，全关 `2.1=0`，停止 `2.1=1`。全部沿用原驱动，单次写入，无超时重发。
- 只更新请求目标不会更新实际位置。确认要求实际位置到达目标并停稳；停止要求有效停止状态。运动命令的协议应答只表示桥接受理，物理完成仍取决于后续可信回读。失败保留最后实际值并通过正常缓存同步标为不可达。
- Matter 端点在等待运动回读时释放自身事务，停止可进入原生优先队列；旧运动迟到结果不能覆盖停止结果。短暂缓存提交的锁等待不会变成等待整段行程。
- 快照、配对和平台 GET 只读共享缓存；桥接不启动新设备轮询。前台默认 5 秒、后台默认 30 秒及用户自定义值保持原逻辑，Matter 约每 5 秒同步缓存，因此平台看到变化有轮询与同步延迟。
- 日志保留 Matter 请求来源及既有逐包记录，不新增凭据或原始私密报文。正常 64 MiB 完整日志及关键日志容量不变。

## 验证与本地复验

云端使用模拟配置，不连接设备。SDK 回归覆盖通用语义（更换型号仍可映射）、电源分离、步长/错误读数、无虚构宠物电源；App 逻辑回归覆盖缓存零额外发包、一次目标写入/确认、Matter 日志来源、异常前置读取无写入、无 2.5。真实 matter.js 端点回归覆盖方向换算、Heat/Off 与温度步长、回滚、运动中停止、迟到结果和缓存/命令并发。

在干净 Mac checkout 上先做离线验证，保持正式 App、桥接、配置和配对不动：

```sh
swift test --force-resolved-versions --filter 'PanelMemoryTests|PanelToggleTests|MatterAppliancePlanTests|CurtainInteractionTests|MatterSnapshotPollingTests'
bash scripts/validate_macos.sh
```

脚本使用 Node 22；Matter 测试的 App IPC 使用独立测试端口，保留正式 5540 桥接。云端 Linux 平台替身验证不能替代原生 AppKit/SwiftUI 类型检查或界面验收。

后续只有用户授权后才进行界面/实机验收：检查 Matter 列表能力说明；先选择一台卷帘确认位置、开关停和原米家共存，再检查加热/照明电源分离与温度步长。Aqara M200 固件和 Aqara Home 版本在报告中均未取得，M200 配对、平台显示范围及长期控制均未验证。不将模拟、历史只读值或 Matter 应答表述为本轮实物动作成功。
