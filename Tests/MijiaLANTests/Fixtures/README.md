# Reviewed specification projections

These fixtures are hand-reviewed projections of public specification pages, initially reviewed 2026-11-04 and extended with the household reports received 2026-11-06. They are **not** raw device responses or complete official instance JSON. Device URNs/versions, service/property IDs, formats, access and the listed ranges/enums are preserved for the selected regression cases; unrelated services and some options are omitted. Property/service `type` fields use semantic short names, not invented full URNs. They are test resources only and do not replace the App’s cached schemas.

Sources:

- https://home.miot-spec.com/spec/dooya.motor.dc1545 — motor-controller v1; MIoT position 0=closed, 100=open; motor-control is write-only.
- https://home.miot-spec.com/spec/xiaomi.derh.13l — dehumidifier v2; environment temperature is float, step 1.
- https://home.miot-spec.com/spec/iot.tow_w.jd015 — towel-rack v1; surface temperature and setpoint are not room temperature.
- https://home.miot-spec.com/spec/giot.heater.v13daf — heater v1; heater and light are separate services; zero fault enum has placeholder label `null`.
- https://home.miot-spec.com/spec/xiaomi.pet_waterer.70m2 — fountain v2; two distinct out-water-interval properties at 2.7/2.11.
- https://home.miot-spec.com/spec/xiaomi.feeder.pi2001 — feeder v3; repeated status properties have distinct comments; inaccessible and one-shot feeding fields must not become readable controls or Matter switches.

The household report received 2026-11-06 confirms all six deployed URNs and firmware versions; see `docs/household-followup-diagnostics.md`. The original dehumidifier projection remains v2, while the deployed device uses v1: `xiaomi.derh.13l.v1.json` separately preserves only its confirmed cached temperature declaration. `household-readings-2026-11-06.json` transcribes the sanitized report, not original network packets. Vendor feeder fields 5.3/5.4/5.6 have confirmed bool/read metadata; the second report records their numeric zero values and unresolved type conflicts. No MijiaLAN/CLI writes have been verified. A fixture using enum label `null` does not authorize replacing an actual JSON null with a healthy value.

The second household report is transcribed in `household-followup-readings-2026-11-06.json`: all nine tested curtain reads failed with -4004, with matching configured/handshake DIDs; feeder 5.3/5.4/5.6 returned JSON number 0 despite the bool declaration. Their names/types/access were cross-checked against the household cache metadata and public v3 specification projection. Numeric values remain raw conflicts. This adds no production coercion or protocol fallback. The feeder action projection uses input 2.8 as documented by Xiaomi's official integration wiki; feeding remains unsupported.

A subsequent user observation reports that all six curtains stay online in Mi Home, respond to the physical remote and report changed state, but do not respond to Mi Home controls. It is tracked separately from the protocol fixture. A single isolation observation has now completed: the App, its Node process and diagnostic CLI were confirmed absent after normal exit, after roughly 30 seconds, and after one user adjustment in Mi Home. The user clarified that the phone command did not drive the curtain, while the physical remote did; Mi Home then correctly updated the displayed state following the physical action. This must not be recorded as a phone command causing a display change or succeeding. Exact state fields/values and physical-remote action counts were not supplied. A LAN scan was accidentally triggered before exit; the quiet interval began only after confirmed process termination. This observation is recorded in the field document, not converted into protocol values or a movement/position fixture. MijiaLAN remains stopped and device probes are paused. Neither this one-device, one-attempt observation nor the read-only tests establishes the cause.

The user subsequently power-cycled the curtain device(s) and confirmed that control in the phone Mi Home app recovered while MijiaLAN remained exited. Device count, exact values and control counts were not supplied. This records recovery after a restart, without establishing the trigger or validating LAN reads/writes, position direction, bridge control or pairing. Failed-read fixtures are unchanged; no post-restart protocol data has been collected.

A later report using the b610a64 client describes order-dependent replies on six firmware-1.1.3 curtains while the installed App was running. `dooya-order-dependent-readings-2026-11-06.json` preserves six described cases weighted to 11 reported requests: a code-zero numeric 2 moves between status and fault when the first requested attribute changes; single position reads still fail. This is not trustworthy state even when it matches a status enum. The subsequent control failure is recorded as temporal evidence without claiming a trigger or mechanism. The exact model is now restricted: no default property polling/probes, no writes or bridge control; connectivity info remains separate. Test responses never authorize new device requests.

Daily control rechecks the same v1 public specification (2026-11-07): 2.1 values 0 Close / 1 Pause (App label Stop) / 2 Open; positions 0 closed and 100 open. `CurtainControlTests` motion sequences are synthetic, not new field evidence. Full travel, Stop, persistent App co-running and six-device operation still require hardware acceptance. Generic protocol/bridge guards remain in place; only explicitly enabled daily sessions can issue these typed writes.
